Module 1: From Building Agents to Designing Solutions

Introduction

Anyone can now build an AI agent in an afternoon. Designing a solution that a business will fund, trust and keep running is a different skill, and it is the skill this course teaches. This module opens with two teams at Harbor Industrial Supply, a distributor whose pricing desk takes 26 hours to answer a quote request. One team builds an impressive agent; the other designs a solution and wins the budget. The difference between them is the design gap.

You will learn to ask, for every step of a process, who should decide what happens next: fixed code, a single model call, a workflow, or an agent. You will meet the four building blocks used in every case in the book, plain code, retrieval-augmented generation (RAG), the agent and the Model Context Protocol (MCP), and see how they work together in one design. In Lab 1 you build a first quote assistant with Google's Agent Development Kit (ADK), connect it to an MCP server, and check where every number in its answer came from.

Before you start Lab 1, complete the Technology Setup page.

Module objectives

By the end of this module, you will be able to:

  1. Explain the difference between building an agent and designing a solution, and name the five design skills this course trains.
  2. Place a proposed system on the autonomy spectrum, from fixed rules to multi-agent systems, and argue for the least autonomy that meets the business goal.
  3. Describe the four building blocks of an agentic solution (plain code, RAG, the agent and MCP), what each contributes, and how each one fails.
  4. Decompose a business process into steps and assign each step to a building block.
  5. Set up and run a minimal ADK agent that calls a tool served by an MCP server.
  6. Name the Google Cloud services that support each stage of the production lifecycle.

Module 2: The Designer's Toolkit

Introduction

A design that lives only in someone's head cannot be reviewed, compared or improved. This module gives you the toolkit used in every case for the rest of the course: a fixed diagram notation called the solution graph, a seven-step design method, the two patterns that appear in almost every design, and a disciplined way to choose between alternatives.

You will practise the toolkit on a new problem, product returns at Harbor. You will draw three alternative designs, score them on eight evaluation criteria in a trade-off table, check whether the winner survives a change of weights, walk the chosen design node by node to find where it can fail, and record the final choice in a decision record. In Lab 2 you measure two of the designs on synthetic return requests and update the trade-off table with real numbers instead of estimates.

Module objectives

By the end of this module, you will be able to:

  1. Draw a solution graph using the book's node types, edge types, boundaries and trace tags, and check it against the well-formedness rules.
  2. Apply the seven-step design method to a business process to produce the inputs for a solution graph.
  3. Apply the retrieve-then-answer and approval-gate patterns, and recognize the three most common anti-patterns.
  4. Score alternative designs on the eight evaluation criteria, weight the criteria from the business context, and test whether the decision survives a change of weights.
  5. Walk a design node by node to find its failure points, and record the final choice in a decision record that states what would change it.

Module 3: The Business of AI Solutions

Introduction

Every design in this course has to answer a sponsor's question: is it worth building? This module adds the business layer that turns a technical design into a decision someone can fund. It takes an information systems view: an AI solution is judged by what it changes in the organization, not by how capable the model is.

Returning to Harbor's pricing desk, you will map the current process to find where time, cost and errors arise, identify the sponsor, users, approvers and owners, and connect the business result to measurable KPIs through a KPI tree. You will then put money on the design: a value case with benefits and costs, unit economics per transaction, and the cost of errors, including errors whose costs are very different. The module ends with a pilot plan with go/no-go criteria and the one-page memo to the executive sponsor that closes every case. In Lab 3 you build a value case and find the one assumption it depends on most.

Module objectives

By the end of this module, you will be able to:

  1. Draw a current-process map that shows where time, cost and errors arise, and use it as the baseline for every claim of improvement.
  2. Identify a solution's sponsor, users, approvers and owners, and state what each needs from the design.
  3. Build a KPI tree that links a business result to operational measures and to the technical metrics of individual components.
  4. Write a value case with benefits, run costs, build costs and payback, and test which assumption it depends on most.
  5. Quantify the cost of errors, including asymmetric errors, and use it to set error budgets.
  6. Plan a pilot with go/no-go criteria and an owner, and summarize the case in a one-page memo to the executive sponsor.

Module 4: Case: A Company Policy Assistant

Introduction

This is the first full case. Alder & Finch, an engineering consultancy with 3,200 employees in three countries, receives about 2,600 policy questions a month, and the answers depend on the employee's country, grade and the current version of each policy. The starting point is a published Google sample agent that answers questions from documents. Your task is to critique it with the toolkit from Modules 2 and 3 and redesign it for this business.

The technical focus is retrieval quality and your first deployment. You will make retrieval permission-aware, current and cited, so that employees see only the policies that apply to them and every answer shows its source and version. The business focus is defining KPIs for a product whose output is information, without falling into the deflection trap. In Lab 4 you deploy the redesigned assistant to Cloud Run and measure retrieval separately from the final answers, including whether restricted content ever leaks.

Module objectives

By the end of this module, you will be able to:

  1. Critique a published retrieval-augmented agent against the design method and well-formedness rules.
  2. Define KPIs for an information product without falling into the deflection trap.
  3. Redesign retrieval to be permission-aware, current and cited, and explain what each change costs.
  4. Deploy an ADK agent to Cloud Run with identity, least-privilege access and event-driven index refresh.
  5. Measure retrieval quality separately from answer quality, using recall, rank, citation, abstention and leakage metrics.

Module 5: Case: Customer Support Triage

Introduction

Cymbal Home & Garden, a home-improvement retailer, handles about 52,000 customer contacts a month by chat and e-mail: order status, delivery problems, returns, product questions and complaints. Google's customer-service sample shows one way to automate this with a single agent. In this module you critique that design and compare it with alternatives, from a triage router to agent assistance for human representatives.

The technical focus is MCP tool design. An agent is only as safe as its tools, so you will redesign the sample's tools to be task-shaped, identity-safe, validated, idempotent and policy-enforcing, and implement one as an MCP server. The business focus is unit economics: a cost-per-contact model, built intent by intent, that tells you which kinds of contact to automate and which to leave with people. In Lab 5 you deploy the agent to Agent Runtime with its tools on Cloud Run, and evaluate whether it calls the right tools, not only whether its answers sound right.

Module objectives

By the end of this module, you will be able to:

  1. Critique a tool-using agent's tool set and callbacks against principles of tool design.
  2. Design MCP tools that are task-shaped, identity-safe, validated, idempotent and policy-enforcing, and implement one such server.
  3. Build a cost-per-contact model that compares designs by intent, and use it to choose which intents to automate.
  4. Pair a containment KPI with re-contact and satisfaction measures so that it cannot be gamed.
  5. Deploy an agent to Agent Runtime with its tools on Cloud Run, and evaluate tool use as well as answers.

Module 6: Case: Invoice to Payment

Introduction

When a workflow moves money, the most important design decisions are about people: who reviews what, what they see, and what happens when nobody responds. Meridian Foods, a food-service distributor with 1,900 suppliers, receives about 9,500 supplier invoices a month. Starting from Google's event-driven expense-approval sample, you will redesign the accounts-payable process from invoice receipt to payment.

The technical focus is human-in-the-loop design. You will decide which invoices a person reviews by comparing the cost of review with the expected cost of errors, and see why the usual rule, review everything above a dollar amount, is often the wrong one. You will design a human checkpoint in full, including how to detect rubber-stamping, and build it as an ADK workflow that routes in code and pauses for a person's decision. The module ends with a rollout that runs in shadow mode before the system is allowed to act. In Lab 6 you build the checkpoint and test that it holds when someone tries to bypass it.

Module objectives

By the end of this module, you will be able to:

  1. Critique an event-driven approval workflow, including how it reads human decisions.
  2. Choose which items a person reviews by comparing the cost of review with the expected cost of errors, and explain why amount thresholds are usually the wrong rule.
  3. Design a human checkpoint: what the reviewer sees, what they may decide, who may decide what, what happens when nobody decides, and how to detect rubber-stamping.
  4. Build an ADK workflow with routing in code and a pause for human input.
  5. Plan the rollout of a money-moving workflow through shadow mode before it acts.
